## Usage Rules

### Completing a Task

When a task is completed through `/done` or `/Done`:

1. Remove it from the active list where it currently exists.
2. Add it to this file.
3. Preserve the original estimated time.
4. Record the actual time spent.
5. Record the completion date.
6. If the task belongs to a project, update the project page and project index as required.
7. If the completed task was the project's current Next Action, promote the next project Next Action according to the project rules.

### Time Tracking

For tasks with an estimate, preserve both:

* **Estimated time** — the original estimate before execution.
* **Actual time** — the time actually spent, supplied by the user.

Example:

`✅ Replace a broken drawer handle — estimated: 30 minutes, actual: 40 minutes`

The purpose of recording both values is to create data points for improving future time estimates.

If `/done` is used without an actual duration, **do not guess the time**. Ask:

> **How long did it take?**

Only close the task after the actual time has been provided.

### Historical Entries

Previously completed tasks may be retained even when they do not contain an estimated or actual time.

Do not invent missing historical information.

Historical completion entries should remain available so the repository preserves a useful record of completed work.

### Project Completion

When a completed task is the current Next Action of an active project:

* Mark the task as completed on the project page.
* Remove it from the project's active Next Actions.
* Promote the next Next Action from the project page.
* Update `Projects/00-Projects.md`.
* Keep exactly one current Next Action for the project in the project index.
* Preserve the project's total estimated time.
* Re-sort the project index by the new Next Action's priority and estimated time.

If there is no remaining Next Action, do not invent one. Indicate that the project may be ready to close or requires the user to define its next step.

### Data for Estimate Calibration

Completed tasks provide historical data for GTD coaching.

When reviewing completed work, compare:

* estimated time
* actual time
* recurring patterns of underestimation or overestimation

Use these patterns to improve future estimates, but do not retroactively change the original estimate.

## Weekly Review

During the Weekly Review, review recent completed items for:

* useful progress and accomplishments
* unusually large estimate deviations
* recurring estimation patterns
* projects that may have advanced or become ready to close

The Done list is primarily a **historical record**, not an active task list.

## Core Principle

Completed work should leave the active system and remain visible here.

The goal is to maintain a trustworthy history of what was completed while preserving the information needed to improve future GTD decisions and time estimates.
